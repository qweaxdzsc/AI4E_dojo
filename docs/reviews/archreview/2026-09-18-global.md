## 先给结论

Dojo 现在不是“缺少一个通用 Trainer”或“缺少几个测试”的阶段。它已经有一条能工作的研究闭环：模型/数据能力放在 contrib，领域流程放在 application，recipe 负责可读的研究顺序，TrainingRun 和 Task 负责运行与产物，Web 只开放经过登记的外流案例。

真正需要架构师持续盯住的是：**这条闭环能不能随着新模型、新数据集和新科研案例增加，仍然保持低接入成本、科学语义不被抹平、研究入口不分裂、Agent 能按需找到正确代码。**

本轮不把上一版的两项局部意见列为核心建议：文档陈述冲突和某个累积配置的零更新边界，最多作为维护事项。

## 一、当前整体形态

### 1. 研究轨和平台轨是两条不同产品路径

源码事实：

- 研究轨覆盖外流 CFD、参数化 PDE、耦合物理场、控制轨迹和时空预测；入口是 recipes、examples、Task 和 Python。
- 平台轨的官方模型/案例目录由 `packages/ai4e-server/modules/capabilities/model_cases.py` 中的 `MODELS`、`CASES` 管理，目前是 AB-UPT、Transolver-3 与 ShapeNet-Car/NASA CRM 外流组合。
- 架构正文明确 PDE、GenCP、SafeDiffCon、WDNO 主要通过 Python/recipe 使用，Web 并未承诺自动开放所有模型。

这不是实现错误，而是当前产品分期。但随着案例增加，必须把“研究能力何时晋级为 Task 能力、何时晋级为 Web 官方案例”说清楚。否则每个新模型都会在 recipe、Task、server capability、Web 页面之间形成一套临时判断，研究轨和平台轨会逐渐分叉。

### 2. 共享的是训练内核和运行外围，领域生命周期仍各自实现

源码事实：

- `ai4e-core/applications/base/iteration_training.py` 与 `abilities/training/*` 已共享更新、恢复、EMA、调度、取消和检查点推进。
- 但 aero CFD、parametric PDE、coupled physics、pde_control、spatiotemporal PDE 各自拥有 preparation、model/train、infer/post 和 handoff 连接；例如 `aero_cfd/train/fitting.py`、`parametric_pde/train.py`、`coupled_physics/train.py`、SafeDiffCon/WDNO 的 contrib training/handoff。
- 这些差异有科学理由：多场模型的场组和选优、控制问题的校准/安全约束、WDNO 的轨迹/小波语义，不能被一个统一流程吞掉。

当前架构的关键问题不是“这些代码为什么不完全相同”，而是要持续判断：哪些重复只是领域语义的必要表达，哪些重复已经是跨案例共同的生命周期工作（输入解析、准备消费、检查点身份、固定结果、指标登记、恢复和 Task 资产交接）。现在共享训练内核已经提炼了一部分，但跨应用的准备/结果/恢复边界还需要用案例证据继续校准。

### 3. Recipe 可读性和平台复用之间存在长期张力

源码事实：

- 五类 recipe 都让 Python 决定顺序，YAML 只放参数和阶段选择；这是研究者可读、可复制的优点。
- 但每个领域仍有一套阶段文件和 configuration/connection 代码。`recipes/aero_cfd`、`gencp`、`parametric_pde`、`safediffcon`、`wdno` 的正文数量和阶段命名并不相同。
- Task 当前通过 `pipeline.py`、`config.yaml` 和 `inputs.*` 投影发现入口；Web 则通过 server capability 和官方案例登记进入。

这条设计目前保护了研究自由，但规模扩大后会出现两个风险：一是相近模型的 recipe 复制越来越多，二是 Agent 必须同时理解 recipe、application、贡献能力和平台登记才能完成一次接入。简单建立全仓统一 workflow 会破坏可读性；完全依赖个人经验又会增加接入成本。

## 二、三个真正重要的架构议题

### 议题 A：建立“研究能力 → Task → Web”的渐进式产品边界

**重要性**：这是决定新模型接入后能走多远的总路线，不是某个页面功能。

**最小架构动作**：不建立全仓注册表，而是在现有模型集成目标、recipe、Task 和 server capability 之间补一张“晋级边界”说明：

- 研究能力：能由 recipe 运行、修改和保存科学结果。
- Task 能力：具备稳定的输入捕获、运行身份、恢复、资产和指标交接。
- Web 官方能力：除 Task 合同外，还具备页面所需的 capability 描述、模型/数据候选、预检和正式入口验收。

每个新案例明确自己停在哪一级，以及进入下一级缺什么证据。这样研究轨可以自由发展，平台轨也不会被迫为所有模型提前建页面。

**职责**：集成目标与 recipe 文档说明研究级要求；Task 负责可托管运行合同；server/web 只维护已晋级案例的产品能力。不要把 Web 登记倒灌成算法包的全局协议。

**科学语义与迁移**：不改变模型、数据、训练或推理算法；只是明确交付层级和未开放边界。已有 recipe 和 Task 保持兼容。

**验收**：选一个已在 Task 可运行但未开放 Web 的模型，再选一个 Web 官方外流案例，逐项对照输入、恢复、资产、指标、候选描述和页面操作，能清楚说明两者差异。以后新模型集成报告必须声明晋级级别。

**可量化收益**：以后每个模型只需回答一份边界清单，减少“已经能跑”与“已经平台化”的混淆；具体节省时间需后续真实案例统计，当前不虚报百分比。

### 议题 B：围绕研究生命周期提炼“最小共享交接”，而不是统一算法协议

**重要性**：这是减少跨案例重复代码、又不抹平科学差异的核心。

**最小架构动作**：以已有 `inputs`、TrainingRun、资产索引和固定结果为基础，持续识别四个可跨领域的交接：

1. 输入来源及其身份；
2. preparation 的消费条件和冻结语义；
3. checkpoint/weight group 的来源、结构和恢复边界；
4. 固定 prediction/result 与指标的来源、单位和评价口径。

每个交接只规定“谁拥有、如何证明来源、失败如何暴露”，不规定模型内部对象、张量布局、损失函数或统一 pipeline。领域 application 继续负责把本领域对象接到这些交接上。

**职责**：spec 只承载确实跨进程/持久化的稳定信息；core 提供通用写入、读取和生命周期工具；contrib/application 提供模型/领域解释；recipe 只表达顺序和局部连接；Task/Server 只消费已声明交接。

**科学语义与迁移**：不把 GenCP 多场权重组、SafeDiffCon 控制响应、WDNO 轨迹清单或 CFD 网格准备强行变成同一种科学格式。只有在两个以上真实案例重复且语义一致时才提炼共享能力。

**验收**：选外流 CFD、GenCP、SafeDiffCon、WDNO 四类案例，画出从输入到 preparation、训练权重、固定结果、指标的所有权和消费关系；标出重复实现与不可共享差异。若某交接无法在两类以上案例中保持同一语义，就留在领域层。

**可量化收益**：衡量新案例为生命周期交接新增的代码行、重复适配点和跨层文件数；目标是让重复的外围交接减少，而不是让领域算法文件变短。

### 议题 C：为 Agent 和研究者建立“按任务定位”的架构入口

**重要性**：当前模块边界清楚，但案例越多，单靠目录和长索引越难让 Agent 快速找到正确修改点。

**最小架构动作**：强化已有 `.context/tasks/research.md` 和模型集成 skill，使其每次以任务问题为入口回答四件事：

- 我要新增模型/数据集/案例，先看哪个 application 和 recipe；
- 我要改训练策略、恢复或推理，哪些 core 能力可以直接复用；
- 哪些参数和文件属于科学语义，不能由框架替换；
- 该能力目前处于 recipe、Task 还是 Web 哪一级。

这不是新增全仓组件注册表，也不是把所有代码压缩成一份自动生成说明。它是面向任务的“定位—边界—证据”入口，最终仍以源码和 PRD 为准。

**职责**：`.context/tasks` 负责任务路由，模块索引负责目录职责，PRD 负责长期行为，集成 skill 负责模型准入和证据边界；不能让任何一层复制完整架构正文。

**验收**：用“接入新模型”“增加数据集”“替换训练策略”“把 Task 能力开放到 Web”四个任务做盲定位，由人或 Agent 从入口找到正确 application、recipe、core、Task/server 文件，并能说清不该改的层。记录首次定位路径和误入文件数量。

**可量化收益**：关注首次定位耗时、误读文件数和重复询问次数；不把链接数量或测试数量当作理解效率。

## 三、架构师结论

Dojo 当前最值得保留的是“科学代码自由、共享运行外围、平台逐级开放”的方向。最需要建设的不是一个更大的抽象层，而是三件事：

1. 让新模型知道自己从 recipe 到 Task 到 Web 的晋级路径；
2. 只提炼真实跨案例重复的生命周期交接；
3. 让人和 Agent 按研究任务快速定位实现、边界和证据。

上一版两个局部建议降为维护观察，不进入核心路线图。后续架构复审应优先检查上述三个议题在新模型/数据集/案例接入中是否被真实触发和验证。
