# Dojo 与五个 AI4S 框架的能力比较及案例驱动演进参考

分析日期：2026-09-10。定位：研究与升级参考，不是架构实施计划或功能承诺。

## 1. 已确认的发展路线

**优先接入新的模型、数据集和案例，用 Dojo 真正开展科研研究，再利用这些案例暴露的问题持续增强和打磨框架。**

判断一次接入是否有价值，应看它能否支持一个真实研究问题、产生可解释的实验结果，以及揭示现有工作流的复用边界。新增模型数量、配置数量或目录数量本身不代表研究能力增强。

此前比较提出的“统一训练入口能力、稳定扩展契约、补充物理能力与公平基准”三个优化方向，**当前不作为独立实施任务，也不作为接入新案例的前置条件**。本文保留相关能力作为参考：当真实案例遇到瓶颈或重复需求时，再决定需要借鉴什么、修改哪里以及如何验证。

建议沿用以下工作顺序：

1. 确定研究问题，选择相应模型和数据集。
2. 在现有框架上接入案例，完成数据准备、训练、评价与结果分析。
3. 记录接入过程中的重复实现、难以表达的语义、运行瓶颈和实验可信度问题。
4. 根据案例证据做必要的局部改进；出现跨案例共同需求时，再提炼为共享能力。
5. 用新案例和受影响的已有案例验证改进，保留实验条件与结果。

这条路线不排斥架构优化，而是让架构优化由科研使用事实驱动。本文不指定下一批模型、数据集或接入顺序。

## 3. 六个框架的主要定位

| 框架 | 主要能力与优势 | 使用成本或局限 | 对 Dojo 的参考价值 |
| --- | --- | --- | --- |
| Dojo | 工程物理数据、模型准备、训练、预测回贴与实验比较之间的显式交接 | 正式研究证据集中在外流 CFD 与两类模型；共享路径仍有执行限制 | 用新研究案例验证已有分层和产物约定能否复用 |
| Noether | 科学模型训练运行时，批量、精度、DDP、回调与恢复较完整 | 扩展需理解其模型、训练器和配置协议 | 当案例需要复杂训练控制时，参考运行时设计 |
| PhysicsNeMo | PyTorch 科学模型、网格表示、GPU 与分布式组件；已有统一外流流程 | 核心与领域生态需要组合，部分模型和数据支持仍标注待提供 | 新工程模型、大点云或多卡案例的直接技术参照 |
| PaddleScience | 方程、几何、约束和 Solver；物理驱动、数据驱动与混合求解 | 依赖 Paddle 生态，PyTorch 模型需适配 | 物理约束、边界条件与多目标研究的参考 |
| MindScience | MindSpore 科学组件、可微求解器及多领域套件 | 不同领域与案例入口存在差异，PyTorch 模型需迁移 | 新领域案例与可微物理组件的参考 |
| Anemoi | 气象数据、图构建、训练和推理的系统化协作及元数据交接 | 气象领域假设较强；官方标注 Incubating；本次训练源码证据有限 | 时序预测、数据版本和训练推理一致性的参考 |

各框架的重点不同，不适合根据功能数量给出单一总排名。

## 4. 各框架能力、优势与可借鉴之处

### 4.1 Noether：训练运行时的直接参照

**已检查的能力。** Trainer 配置包含精度、有效批量、回调、初始化和恢复等声明；实现中有 DistributedDataParallel 包装、混合精度上下文与 torch.compile 接入。

**优势。** 常见训练控制集中在运行时，案例可以复用批量、分布式、回调与检查点机制。对需要长时间训练或复杂实验控制的研究，这些机制比单独复制训练脚本更容易保持一致。

**局限与成本。** 扩展时需要理解其 Model、Trainer、配置与回调生命周期。不能因此认定它缺少数据处理或后处理，也不能仅凭 Dojo 的接口较少就判断 Dojo 扩展更容易。

**案例触发的借鉴。** 当新案例需要多卡、有效批量、特殊训练回调或恢复策略时，先参考它已有的处理方式，再决定 Dojo 是否需要共享实现。

来源：[Trainer](../../noether/src/noether/training/trainers/base.py)、[回调](../../noether/src/noether/core/callbacks/base.py)、[仓库说明](../../noether/README.md)。

### 4.2 PhysicsNeMo：工程模型与规模化计算的直接对标

**已检查的能力。** DistributedManager 组织分布式环境和进程组，ShardTensor 支持分片张量相关操作。统一外流 recipe 使用 DomainMesh 和模型输入映射，并在训练源码中接入 DDP、混合精度和检查点。

**优势。** 当前统一外流说明已覆盖 Transolver、GeoTransolver、GLOBE 等模型路线，共同处理物理字段、无量纲化、归一化和物理量预测。数据与模型可以在同一工作流中组合，规模化训练有现成组件参考。

**局限与成本。** 核心、领域 recipe、Curator 等生态组件存在整合成本。统一外流说明中的 DoMINO 和部分数据集仍标注 coming soon，不能因为配置目录存在就视为已完成支持。GPU 优化是否适合某个案例，仍需在实际设备上验证。

**案例触发的借鉴。** 接入大规模网格、多域模型或多数据集研究时，参考其物理表示、字段到模型参数的映射、无量纲化、数据加载和并行方式。

**对 Dojo 定位的修正。** “统一 CFD 工作流”“多模型共用数据”不是 Dojo 独有优势。Dojo 应通过实际案例证明自己在接入成本、交接检查、实验追踪和比较可信度上的价值。

来源：[统一外流说明](../../physicsnemo/examples/cfd/external_aerodynamics/unified_external_aero_recipe/README.md)、[训练实现](../../physicsnemo/examples/cfd/external_aerodynamics/unified_external_aero_recipe/src/train.py)、[分布式管理](../../physicsnemo/physicsnemo/distributed/manager.py)、[分片张量](../../physicsnemo/physicsnemo/domain_parallel/shard_tensor.py)。

### 4.3 PaddleScience：物理问题表达与约束组合

**已检查的能力。** Solver 接收 model、constraint、equation、geometry、validator、visualizer 等对象，同时处理优化器、训练控制、混合精度和分布式相关设置。框架说明包括符号方程、高阶微分及不同边界条件。

**优势。** 方程、区域、边界、损失和求解过程之间的关系明确，适合 PINN、监督学习及数据物理融合研究。物理问题表达已有较丰富的组织方式可参考。

**局限与成本。** 依赖 Paddle 生态。现有 PyTorch 模型、算子与检查点不能假定直接复用；求解器抽象的关注重点也不等同于工程资产和运行产物管理。

**案例触发的借鉴。** 当某个科研案例确实要加入 PDE 残差、边界约束或多种损失时，参考它如何将物理问题与训练机制分开。无需为了功能对齐先移植整个 Solver。

来源：[Solver](../../PaddleScience/ppsci/solver/solver.py)、[仓库说明](../../PaddleScience/README.md)。

### 4.4 MindScience：多领域应用与可微物理

**已检查的能力。** PDEWithLoss 使用符号表达与 Jacobian/Hessian 相关能力组织方程计算；框架包含可微求解器、科学算子和多个领域套件。抽查的 MindFlow Transolver 案例自行组织训练、评价与检查点保存。

**优势。** 为流体、化学、生物、地球科学等方向提供领域应用和科学计算组件，是寻找新案例和物理算法实现方式的重要参考。MindSpore/Ascend 路线也有其生态价值。

**局限与成本。** 多领域覆盖不等于所有模型共用同一种训练接口；不同套件及案例需要分别检查。迁移 PyTorch 模型存在适配成本。本文没有验证 README 中的性能宣传或所有领域能力。

**案例触发的借鉴。** 当 Dojo 开始做热传导、结构、瞬态或其他实际研究时，参考对应领域的数据语义和物理组件，再检验 Dojo 的 application 分工是否适用。

来源：[PDEWithLoss](../../mindscience/mindscience/pde/pde_with_loss.py)、[Transolver 案例](../../mindscience/MindFlow/applications/data_driven/transolver/exp_elas.py)、[仓库说明](../../mindscience/README_CN.md)。

### 4.5 Anemoi：跨阶段元数据与领域系统协作

**文档明确的能力。** Anemoi 由数据、图、模型、训练、推理和变换等包构成，强调元数据由上游收集、下游消费。README 声明使用 Lightning、Hydra、Zarr、Xarray 等，并提供系统级集成测试。

**优势。** 从气象数据准备到预测交付的系统链条清楚，适合研究如何让训练和推理共用变量定义、变换和来源信息。

**局限与成本。** 时间轴、气象变量、预报步长和图结构带有领域假设，不能直接套到所有 CAE 案例。官方标注为 Incubating。本次本地目录不含训练核心子包，不能据此确认其每项运行细节。

**案例触发的借鉴。** 当新案例涉及时间序列、滚动预测、大规模分块数据或跨包部署时，参考其数据生命周期和集成测试思路。PT 与 Zarr 等存储方式应按案例访问需求选择，不把某种格式设为所有案例的必经中间层。

来源：[框架总览](../../anemoi/README.md)、[包职责](../../anemoi/docs/getting-started/package-descriptions.rst)、[系统测试](../../anemoi/tests/system-level/README.md)。

## 5. Dojo 已有的价值与当前边界

### 5.1 值得在新案例中保留和验证的长处

1. **物理数据与模型准备分开。** 同一物理来源可生成不同模型的输入，训练采样与最终完整点场评价分离。已有五案例为两类模型、两套数据的共同工作流提供了证据。
2. **比较可信度有程序检查。** 比较实现检查来源、样本、原点 ID、坐标和真值一致性，拒绝将部分预测当作完整成功。其价值是降低错误实验结论的风险。
3. **实验可编辑，结果可追溯。** 普通 recipe、组件注入、配置与源码快照、准备与检查点交接，支持研究者重复修改、运行和复查实验。
4. **计算与产物消费有分工。** task 和 viz 通过约定的运行产物衔接，有利于在新案例中复用比较与报告流程，而非随模型重写展示逻辑。

这些是已观察到的设计与实现长处，不代表其他框架没有类似能力。是否更适合研究者，仍应通过真实接入与实验使用验证。

### 5.2 当前不能扩大解释的证据

- 五个 example 主要是两类模型在不同数据与域上的组合，不等于五种独立学习范式，更不证明任意 AI4S 任务都能直接接入。
- 共享物理训练路径目前限定 batch_size=1、num_workers=0、FP32，并关闭训练期评价；底层其他路径已有的 AMP、累积和回调能力，不等于在所有入口都已贯通。
- 物理约束尚未在本次核验范围中交付；“物理数据”或“物理模型”命名不能替代实际方程或守恒约束实现。
- 已有单轮、固定五测试样本全点评价主要验证装配与比较链，不证明收敛精度、泛化或框架速度优势。
- 分析时五案例 50 轮验收记录仍标注运行中；本文未检查其实时作业状态，也不把计划报告算作完成。
- AB-UPT 的 MPS 严格数值一致未通过，不能沿用 CPU 或 Transolver 的数值对齐结论。
- 当前工作区已有 Web/Server 实现，本次比较不评价其完整平台成熟度，不能沿用旧索引将其全部视为占位，也不因目录存在宣称平台整体交付。

来源：[共享工作流](../packages/ai4e-core/applications/aero_cfd/workflow.py)、[训练循环](../packages/ai4e-core/abilities/training/loop.py)、[物理准备](../packages/ai4e-core/applications/aero_cfd/trainprep/physical.py)、[比较实现](../packages/ai4e-core/applications/aero_cfd/post/comparison.py)、[跨模型验收](../.context/mvp/cross-model-acceptance.md)、[50 轮记录](../.context/mvp/cross-model-50-acceptance.md)、[AB-UPT 端到端验收](../.context/mvp/abupt-end-to-end-acceptance.md)。

## 6. 用案例触发能力升级的参考表

以下是未来遇到问题时的检索表，不是当前待办清单，也没有预设优先级。

| 科研案例遇到的实际问题 | 优先参考 | 可以考虑的改进 | 以什么事实判断有帮助 |
| --- | --- | --- | --- |
| 新模型输入、输出或训练步难以接入 | Noether、PhysicsNeMo | adapter 和公共组件协议；模型源码独立维护 | 新案例能运行，已有案例不退化；记录需要改动的模块 |
| 重复写多卡、精度、回调或恢复逻辑 | Noether、PhysicsNeMo | 复用运行时能力并贯通案例入口 | 实际设备训练、恢复与评价正确，不以配置开关存在验收 |
| 数据加载或全点预测成为瓶颈 | PhysicsNeMo、Anemoi | 预取、拼批、分片读取、按访问模式选择存储 | 实测阶段耗时、吞吐、内存与显存，验证精度不受不当改变 |
| 研究需要 PDE、边界或守恒约束 | PaddleScience、MindScience | 物理问题表达、算子与损失组合 | 解析场或独立参考验证，加上研究任务中的消融结果 |
| 时间序列或滚动预测难以表达 | Anemoi、MindScience | 时间身份、输入窗口、rollout、时序评价 | 明确数据泄漏边界，预测时间轴与目标任务一致 |
| 多模型结果无法可靠复现或比较 | Anemoi、Dojo 现有比较机制 | 版本、来源、变换与预算记录 | 同一实验条件可还原，差异能定位到数据、模型或执行设置 |
| 多案例反复复制相同处理 | 结合各框架对应实现 | 从重复且稳定的需求中提炼共享能力 | 新旧案例共同使用；保留必要的领域差异 |

当比较成本时，预处理、采样、训练和最终评价应整体入账。固定预算下的精度、达到同等精度的总成本是两种不同问题；不能用单 epoch 或在线推理速度替代端到端结论。模型优劣与框架执行开销也应分别分析。

## 7. 每个新科研案例建议留下的记录

为便于后续总结，案例可以留下以下简短记录；这是研究记录建议，不要求当前新增配置字段或框架模块。

- **研究问题**：希望验证什么假设，基线是什么，什么结果能支持或反驳假设。
- **模型和数据来源**：版本、许可、分片与样本身份，是否修改参考实现。
- **实验条件**：预处理、采样、归一化、训练预算、硬件和精度。
- **实际结果**：指标、物理量、可视化、耗时及失败或未完成部分。
- **Dojo 接入情况**：复用了哪些能力，哪些代码暂时留在案例或 adapter 中。
- **框架反馈**：遇到了什么问题，证据是什么，是本案例特有还是多个案例重复出现。

“能启动”“短训跑通”“参考结果复现”“形成研究结论”分别记录。接入阶段可先打通链路，正式科研结论仍需要匹配任务的实验规模、评价和证据。
